\noindent{\bf [Abstract]}
Prior JOILang studies established a service-level IoT DSL and a reliable NL-to-JOILang generation pipeline. This paper addresses a deployment problem that arises when a prompt written for a cloud LLM is used with local LLMs. Directly reusing the same prompt is unreliable because local models differ in instruction following, code generation ability, context capacity, tokenization, decoding behavior, and prompt sensitivity. We therefore treat a JOILang prompt as a set of functional blocks rather than a single long string. Each candidate prompt is represented with block choices, block versions, detailed rules, example settings, generation settings, and past-failure metadata. The proposed GPS-PromptOps searches these choices with a genetic algorithm while keeping the service context construction fixed. We define three configurations: \emph{CloudRef}, \emph{DirectTransfer}, and \emph{GPS-PromptOps}. CloudRef is the GPT-4.1-mini reference point, DirectTransfer applies the cloud-written prompt directly to local models, and GPS-PromptOps denotes the final prompt selected after GA search and PromptOps selection criteria. The main evaluation was conducted on Qwen2.5-Coder-7B-Instruct, Llama-3.1-8B-Instruct, and Qwen2.5-Coder-14B-Instruct. Across these three local targets, GPS-PromptOps improves DETPass by 3.9--7.0 percentage points (5.2 on average) and ReplayFit by 7.9--17.0 percentage points (11.8 on average) over DirectTransfer, while reducing average input tokens by $65.1\%$ and average latency by $43.7\%$. These results show that a cloud-written prompt is not equally effective for all local models and that local JOILang generation benefits from model-specific prompt optimization using rule-based validation and failure-case feedback.
